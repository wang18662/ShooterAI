# ShooterAI

**盘出 UE5.8 官方 FPS 模板敌人 AI 的九处能力缺口，补齐十一项，做成一套可演示的完整战术行为系统。**

> Unreal Engine 5.8 · C++17 · GameplayStateTree · NavMesh · 反射调用 · UE Python Scripting
> 一个"找缺口并补上"的引擎内 AI 实战项目，不是一个重写引擎已有功能的练习。

---

## TL;DR

**十一项能力，全部接线、全部亲验。**

| 层 | 能力 | 怎么证明它真的有效 |
|---|---|---|
| 移动 | ① **预判追击** —— 追未来位置，不是追尾 | 绕柱横跑 → 斜线截击；`MaxPrediction` 归零 → 退化为直线追尾 |
| 移动 | ② **记忆与搜索** —— 看不见时去最后已知位置找，找不到才放弃 | 屏幕四色流转 绿(追)→青(去记忆点)→品红(原地环视)→退出 |
| 移动 | ③ **群体分离** —— 多敌不叠在一起 | 6 敌围攻时 `最近同伴` 收敛到 ~250cm、分离偏移归零 |
| 战术 | ④ **战术影响图** —— 知道哪片区域危险 | 热力图玩家脚下最红；关掉后撤退变直线后退 |
| 决策 | ⑤ **血量三档** —— ≤60% 边退边打 / ≤25% 逃 / 道具耗尽拼死 | 标签 `RETREAT`→`FLEE`→`DESPERATE` 变色 + 提速 + 停火 |
| 行为 | ⑥ **掩体回血闭环** —— 找掩体 → 蹲下回血 → 被打断换点 | `FLEE`→`HEALING`→`PURSUING`，血量上涨、道具递减 |
| 行为 | ⑦ **双门控停火** —— 视线（几何）× 意图（行为） | 背对逃跑时不开火；蹲着回血时不开火 |
| 战斗 | ⑧ **弹道解算** —— 补偿重力下坠 + 目标提前量 | 2000/4000cm 均命中；`GravityZ` 改回 980 → 远距离飞过顶 |
| 驱动 | ⑨ **边追边打** —— 反射调起蓝图射击函数 | `射击中=1`，AI 边跑边开火 |
| 执行 | ⑩ **行为 LOD** —— 按重要性分档调度思考频率 | 15 敌等效决策次数 15 → ~6 次/帧；降档确认改 1 → 阈值抖动可见 |
| 表达 | ⑪ **行为可视化** —— 染色 / 轨迹 / 状态标签 / 预判点 | 关掉 `AI Path Viz` → 回到纯黑盒 |

每一项都配了 **正测（能生效）+ 反证（关掉就退化）** 两套演示——这是本项目最核心的方法论。

## 一、为什么做这个题

UE 官方 FPS 模板（Variant_Shooter）的敌人 AI 有一个明确的设计定位：它是**射击靶场**，不是**追猎者**。逐项盘查后，确认九处能力缺口：

| # | 缺口 | 玩家看到的现象 | 根因 | 层 |
|---|---|---|---|---|
| ① | **不追人** | 敌人"朝我之前的位置走过来，然后站定开枪" | StateTree 只有 `Roam` / `Sense` / `Shooting`，**没有 Chase 状态** | 移动 |
| ② | **没有记忆** | 我一躲到柱子后，它立刻回去巡逻 | 只有"看得见就追"和"看不见就放弃"两个极端 | 移动 |
| ③ | **多敌挤成一坨** | 几个敌人叠在同一个点 | 同一个目标点 + 同一条寻路结果 | 移动 |
| ④ | **不知道哪里危险** | 直线冲向玩家，穿过火力覆盖区 | NavMesh 只给**最短**路径，不知威胁分布 | 战术 |
| ⑤ | **所有 AI 同频思考** | 远处看不见的敌人也每帧跑完整 StateTree | 没有按重要性分配算力的机制 | 执行 |
| ⑥ | **只追不打** | 进了 Chase 就再也不开火 | `Chase` 里没有射击 Task；模板的 `Shoot at Target` 因类型不兼容**永远绑不上** | 驱动 |
| ⑦ | **不会怕死** | 快被打死了还往前冲 | 没有按血量调整行为 | 决策 |
| ⑧ | **远距离打不中** | 子弹下坠、移动目标打空 | 瞄准是纯直瞄，**不算重力也不算提前量** | 战斗 |
| ⑨ | **行为不可见** | 观察者只看到"敌人冲过来了" | 决策是纯逻辑，没有外显 | 表达 |

选这个题的理由：**短板是真实的、可验证的、边界清晰的**。我不重写寻路和渲染——只做「AI 该在哪一层做什么」的判断。

## 二、架构

项目是**蓝图为主 + 自写 C++ 组件**的混合结构。C++ 侧按职责拆成 4 个 `.cpp`（**类定义不变，蓝图与调用点零改动**）：

```
Source/ShooterAI/
├── PursueSteeringComponent.h          ← 组件定义 + 9 节章节地图
├── PursueSteeringComponent.cpp        ← 核心：追击算法 / 分离 / 导航投影 / 引擎桥接
├── PursueSteeringComponent_Health.cpp ← 血量读写 / 档位 / 回血道具 / 受伤谨慎
├── PursueSteeringComponent_Cover.cpp  ← 掩体射线探测（安全 = 看不到，不是距离远）
├── PursueSteeringComponent_Legacy.cpp ← 旧旁路 + 3 个未接线算法（不参与执行）
├── StateTreePursueTask.h/.cpp         ← 行为层：血量闭环 / 掩体选择 / 记忆搜索
├── StateTreeShootControlTask.h/.cpp   ← 开火控制：双门控 + 反射调蓝图
├── BallisticsComponent.h/.cpp         ← 弹道解算
├── TacticalInfluenceMap.h/.cpp        ← 战术影响图
├── AILodComponent / AILodSubsystem    ← 行为 LOD 调度
├── AIPathVizComponent / AITintComponent ← 行为可视化
└── ShooterAIDebug.h                   ← 调试开关与 Key 规范
```

职责分层：

```
StateTree（决策）        现在该干什么：漫游 / 追击 / 撤退 / 回血 / 拼死
      ↓
Task（行为）             血量档位判定、掩体选择、双门控开火
      ↓
Component（能力）        算落点、算掩体、读血量、算弹道、算影响图
      ↓
CharacterMovement       执行位移（引擎负责）
```

模块依赖（`ShooterAI.Build.cs`）：`Core` `CoreUObject` `Engine` `InputCore` `NavigationSystem` `AIModule` `StateTreeModule` `GameplayStateTreeModule`。

## 三、三处核心设计（最值得深挖的三处）

> 全部十一项能力的设计说明见 `项目总结.md`。这里挑三处**最能体现引擎理解**的展开。

### ① 预判追击（Pursue）

移植《AI for Games》3.3.8 的 Pursue：按目标速度外推一个拦截时刻，追那个点。

```cpp
direction  = target.position - character.position;
prediction = (speed <= distance / maxPrediction) ? maxPrediction : distance / speed;
return target.position + target.velocity * prediction;
```

**算法只有三行，真正的工程量在胶水层**，三个必须处理的引擎现实：

1. **预测点可能落在墙里** → 必须过一次 `ProjectPointToNavigation`；投影距离超过 `MaxNavProjectionDistance`（默认 150cm）就**放弃预判，锁人物当前位置**。宁可笨但一定对，也不追一个到不了的点。
2. **UE 的移动指令"后下达者胜"** → StateTree 在 PrePhysics 下 `MoveTo`，我们的组件必须在更晚的阶段下指令，否则会被覆盖。一行解决：`PrimaryComponentTick.TickGroup = TG_PostUpdateWork;`
3. **蓝图的 `CharacterMovement` 才是最终执行者** → 算法只负责算点，不负责动。

### ② 记忆与搜索（Memory / Search）

补上模板缺失的"中间那档"：看不见之后，去你消失的地方找一圈。

```
看得见        ──→ PURSUING  追预判点（绿），同时刷新记忆
   │
看不见
   ↓
记忆未过期    ──→ CHASING   去最后已知位置（青）
   │              ↓ 到达 / 追赶超时
   │           SCANNING   原地环视 4 秒（品红）
   │              ↓ 搜不到
   └──────────→ 返回 Failed，把"放弃后去哪"交还状态机
```

五个刻意的设计判断：

| 判断 | 理由 |
|---|---|
| 记忆存 `FVector` 位置，**不存 `Actor*`** | 存指针的话玩家跑多远都能追，等于没有"丢失目标"这回事 |
| 记忆点必须先过 NavMesh 投影 | 玩家贴墙跑时记忆点会落进墙里，不投影则 `MoveTo` 静默失败 |
| 环视用**转向**，不用随机移动 | 转圈是明确的"我在找"视觉信号；随机游走会被误读成巡逻，且零寻路开销 |
| 放弃时返回 **`Failed` 而不是 `Succeeded`** | `Failed` 才会触发状态机的 `On State Failed` 转换——"放弃后去哪"变成状态机里可配置的，代码不写死决策 |
| 加**追赶超时**兜底 | 记忆点可能不可达（玩家贴柱消失、记忆点在柱子另一侧），此时 `MoveTo` 每帧失败但**不报错**，敌人原地不动、距离却一直大于阈值 → 永远进不了扫描 → 卡到记忆过期 |

> **最重要的设计意图：它会放弃。** 永不放弃的 AI 不是聪明，是赖皮。

### ③ 群体分离（Separation）

```cpp
for each neighbor within threshold:
    direction = my.position - neighbor.position;
    strength  = decayCoefficient * (threshold - distance);
    result   += direction.normalize() * strength;
```

**关键的语义转换**（这是本项目最能体现引擎理解的一处）：

> 源库输出的是**加速度**，再由调用方积分成速度。
> UE 这边走 NavMesh 寻路，直接改速度会穿墙、会和寻路打架。
> 所以我把合力当成**移动目标点的偏移量**——语义从"推着走"改成"绕着追"，
> 群体分散效果一致，但不破坏寻路。

**验证不靠肉眼**，打印两个数一起判：

| `最近同伴` | `分离偏移` | 结论 |
|---|---|---|
| ≥ 220cm | 0 | ✅ 收敛完成 |
| < 220cm | 0 | ❌ 才是 bug（该推却没推） |
| < 220cm | > 0 | ⏳ 还在推 |

两个次生问题（比算法本身更值得讲）：

| 坑 | 本质 | 修法 |
|---|---|---|
| 关掉分离后 `最近同伴` 永远是 `-1` | 一个开关同时控制"要不要测量"和"要不要施加" | **测量与施加解耦**：永远测量，开关只控制施加 |
| 敌人停下开火后就不再分离 | `StopMovement()` 之后直接 `return`，偏移算了但被丢弃 | **站桩让位**：算出「玩家位置 + 外法向×StopDistance + 分离偏移」的理想站位再走过去，并加死区防抖 |

**为什么"偏移归零"不是失效**：6 个敌人围在半径 250cm 的圆上，均匀分布时相邻弦长 = 2R·sin(30°) = 250cm > 分离阈值 220cm → 不产生推力 → 偏移归零。**控制量归零 = 目标达成**，和 PID 误差为零时输出为零是同一个道理。

## 四、另外八项能力：一句话说清

| 能力 | 核心机制 | 关键设计判断 |
|---|---|---|
| **战术影响图** | 6000 半径 / 60×60 网格，双场泛洪（威胁 + 安全）+ 3×3 高斯平滑 | 用「变高重入 + FIFO」替代优先队列，把 3600 格的泛洪压到可接受开销；**重建频率 0.3 秒**（设 0 会吃 10~25ms/帧） |
| **血量三档** | ≤60% 边退边打 / ≤25% 逃向掩体 / 道具耗尽拼死反冲 | **无状态重算**：每帧按血量/道具/视线重新推导，不保存「当前状态」→ 从根上消除卡死 |
| **掩体回血闭环** | 找掩体 → 蹲下回血（每 0.5s +3）→ 被打断换点 → 道具耗尽拼死 | 回血**必须可打断**，否则玩家看着它回血却打不断，整个掩体系统就假了 |
| **双门控停火** | 视线（几何，墙挡不挡）× 意图（行为，该不该打） | 两个 Task 无法互相感知 → 用 Pawn 上的组件做通信通道 |
| **弹道解算** | 补偿重力下坠 + 目标提前量，迭代求解发射角 | **重力必须填 490 不是 980**（子弹有 GravityScale 0.5），填错会远距离飞过头顶且近距离看不出来 |
| **边追边打** | 反射双路径调起蓝图 `Start Shooting` | 模板的射击 Task 因类型不兼容**永远绑不上**，只能用反射绕过 |
| **行为 LOD** | 「距离 + 视野 + 交战状态」评分 → 4 档决策间隔（每帧 / 0.05 / 0.15 / 0.4s） | 升降档用**非对称滞回**（升档立即、降档连确认 3 次）消除临界抖动 |
| **行为可视化** | 敌人染色 + 身后轨迹 + 头顶状态标签 + 目标点标记 | `IDLE` 敌人不画标签——15 个灰标签会糊满画面把关键信息挤掉 |

## 五、四处「单行正确、整体错误」的 bug

这是本项目最值得讲的部分：**四个 bug 都不是语法错误，代码每一行单独看都对。**

| # | bug | 表现 | 根因 | 教训 |
|---|---|---|---|---|
| 1 | **判据打架** | 血量过 25% 就原地卡死 | 掩体点是**在点本身**用射线验的，判断「到没到」却用**距离**（150cm）。而这 1.5 米正好是「从柱子后绕出来」的距离 → 每帧：到达 → 暴露 → 重选 → **又选回同一个点**。位移恒为零 | 同一个物理量不能用两种定义同时做法 |
| 2 | **结构自我否定** | 一直逃、最后变灰，**永远不回血** | 整段血量逻辑写在"看得见玩家"的分支里。但**逃跑成功的必然结果就是看不见** → 掉出分支 → 去走"丢失目标" → 放弃。躲起来正是为了回血，却因为躲起来了而放弃回血 | 分支结构会自我否定，单看每一行都挑不出错 |
| 3 | **双开关互斥** | 拼死阶段一枪不放 | 射击侧残留"血量<25% 就停火"的硬编码，而拼死的触发条件恰好是"血量<25% 且没道具" → 一进拼死就被永久锁死 | 两套开关并存时，更严格的那个赢。**同一个决定只能有一个权威** |
| 4 | **熔断锁死出口** | 只有 FLEE，**永不出现紫色拼死** | `if (可回血 && 未放弃找点){找点} else {清目标点}` —— 放弃找点后每帧清目标点，而"到达掩体→回血"必须有目标点 → 永远进不了回血 → 永远不扣道具 → 拼死永不触发。而熔断标志只在"血量回到 60%"时重置，可血量回不去 | **保护机制会顺手锁死出口**：让保护只影响"还试不试"，不影响"能不能走另一条路" |

> 第 4 个是修第 1 个时引入的，隔了一周才暴露。
> 这类 bug 的共同特征是：**不报错、不崩溃，只是某个状态永远不出现。**

## 七、快速开始

**环境**：UE 5.8 / VS 2022（MSVC v143）/ Windows

```
1. 双击 ShooterAI.uproject（首次会提示编译 C++ 模块，选"是"）
2. 编辑器内 Python 控制台执行：BuildMap.py     # 生成七区测试地图
3. 打开关卡 Lvl_AI_Full，Play
```

> **仓库已全量收录官方角色资产**
>
> `Content/Characters/Mannequins/`（125 MB，UE5 官方 Manny / Quinn + 全套动画）**已随仓库提供**，
> 克隆后可直接打开工程，不需要另外从 UE 模板拷资产。

## 九、Roadmap

### 阶段一：把 [game-ai-toolkit](https://github.com/) 的算法搬进引擎（规划中）

我在另一个项目 `game-ai-toolkit` 里已实现并测试了一套**引擎无关**的 Python + C++17 游戏 AI 库（FSM / 行为树 / A* / Utility / Steering / Agent，跨语言 parity 测试断言输出逐字节一致）。本项目目前只移植了其中的 **Pursue + Separation 两个函数**——下一步是把它变成这套库的**引擎侧落地验证场**。

| 批次 | 接入内容 | 落地形态 | 为什么这个顺序 |
|---|---|---|---|
| P1 | **Steering 全家族**：Seek / Flee / Arrive / Align / Face / Wander / ObstacleAvoidance | `USteeringComponent` 统一输出目标点偏移 | 与现有 Pursue/Separation 同构，改造成本最低，能立刻看见效果 |
| P2 | **FSM** | 用 FSM 替换/对照 StateTree 的敌人行为层 | 拿到同一行为在两种决策框架下的对比数据，是讲**取舍**的素材 |
| P3 | **Utility 效用打分** | 多敌协同：谁去包抄、谁去压制、谁去抢点，用打分而非 if-else | 从"每个敌人各自追人"进化到"小队战术"，是真正的 AI 水平分水岭 |
| P4 | **A\*** | 与 UE `NavMesh` 并行的自研寻路，做路径质量/耗时对照 | 研究性质，输出一份 benchmark 而非替换引擎 |
| P5 | **Behavior Tree** | Boss 行为用 BT，与小怪用的 StateTree 形成分层 | 展示"不同复杂度用不同框架"的判断力 |
| P6 | **Blackboard / EventBus / Agent** | 引入黑板做共享认知，事件总线做"一个敌人发现玩家 → 全队进入警戒" | 从单体 AI 走向**群体 AI**，是 P3 的基础设施 |

**验收标准**：每一批都沿用本项目的 **正测 + 反证** 方法——有关闭开关的对照组，有可打印的量化判据，不接受"看起来对了"。

### 阶段二：把 LLM 接进敌人决策（规划中）

目标不是"让敌人说话"，而是**让 LLM 做高层意图、让确定性系统守门**：

```
LLM（意图）  "该撤退了" / "叫增援" / "绕到侧翼"
     ↓
Validator（守门）  字段写白名单 + 数值范围校验，越权直接拒绝
     ↓
StateTree（执行）  只接受合法状态转移，转移表才是状态的唯一权威
```

这条链路在 `game-ai-toolkit` 里已用 `LlmBrain` + `Validator` 验证过（含"越权写 `gold=999` 被拒绝"和"断网时降级模板台词、FSM 照常工作"两个用例）。**核心原则：绝不能用 LLM 去校验 LLM。**

配套的**设定一致性**方案也已单独验证：用 RAG（按语义段落切块 → 滑动窗口重叠 200/50 → BGE 中文向量 → FAISS 内积检索）把 NPC 人设/世界观注入上下文，从构造上压制设定幻觉，而不是靠 prompt 里写一句"别编"。

### 阶段三：可演示的成品

- 1 分钟 demo 视频（预判斜插 / 四色搜索 / 六敌不扎堆 / 参数归零反证）
- 打包可执行版本

## 十、已知限制（诚实清单）

| 限制 | 真实现状 |
|---|---|
| **美术资产** | 全程灰盒，沿用 UE 模板几何体。**没有建模/动画/特效** |
| **内容量** | 自建 1 张七区测试地图（`Lvl_AI_Full`），其余沿用模板关卡 |
| **性能压测** | 只在编辑器 PIE 里跑，最多 15 敌。**未打包、未真机、未做 30+ 同屏** |
| **网络同步** | 完全没有，纯单机 |
| **平衡性数据** | 只有作者一人测，**没有真实玩家数据调难度曲线** |
| **三个算法未接线** | Arrive / CollisionAvoidance / Wander 已移植但**零调用**——UE 已有接近减速、物理碰撞已防重叠、游荡在 demo 里不可辨。这是**主动放弃**，不是遗漏 |
| **旧旁路保留** | `AutoPilotTick` 是 Task 架构之前的方案，Task 模式下强制关闭，保留作隔离调试用 |
| **行为 LOD 的收益口径** | 「省 89% CPU」依赖敌人分布；**可复现的指标是「等效决策次数 15 → ~6 次/帧」** |
| LLM 决策层 | **未做**，只在 Roadmap 阶段二 |

> **这些缺口里没有一个是「AI 逻辑不够好」。** 缺的是美术、性能、网络、内容量——那是团队和预算的问题。

## 十一、这个项目沉淀下来的四条通用原则

不是 UE 专属的，可以搬到任何工程的调试里：

1. **任何失败路径都必须留痕。** 一个静默的 `if (!Comp) return Failed;` 和一个"状态被别人结束了"在现场看起来完全一样，永远分不清。
2. **"关掉某功能"的实验，必须先保证关掉后仍然可观测。** 否则测量和施加被同一个开关关掉，结论必然误判（这就是分离功能 A/B 对比翻车的根因）。
3. **探针要放在所有 early return 之前。** 区分"压根没跑"和"跑了但没输出"，是两类完全不同的 bug。
4. **保护机制会顺手锁死出口。** 熔断/黑名单本质是"给系统加一个提前退出的口子"，但退出口子如果和正常流程共用同一组状态变量，就会把正常路径一起堵掉。让保护只影响"还试不试"，不影响"能不能走另一条路"。
